## Overview

**Milestone Goal:** Every purchase-flow outcome (not just completed) reaches Klaviyo, so Trading Cult can see failed/expired attempts alongside completions. Source ticket: cmqtl47g4004zny0kz54mmz0z (Trading Cult).

Coverage-gap bugfix on the existing Tracking/destinations dispatch framework (shipped in v1.3) — `purchase_failed` was a complete, registered event with zero real callers. **Goal**: Every genuine customer-facing failed/expired/cancelled payment reaches Klaviyo with a usable failure reason, exactly once, while internal bookkeeping status flips stay silent.
**Depends on**: Phase 12 (reuses the `emitTrackingPurchaseCompleted` pattern + stable-eventId convention + dispatcher/adapter framework shipped in v1.3; no new architecture)
**Requirements**: KLAV-01, KLAV-02, KLAV-03, KLAV-04
**Plans**: 3 plans (2 waves)

**Success Criteria** (what must be TRUE):
  1. A payment that expires via the hourly expiry cron fires `purchase_failed` and it is visible in Klaviyo as a "Purchase Failed" event
  2. A payment that fails/expires/is cancelled via any real gateway webhook (Stripe, FanBasis, PayPal, NOWPayments/crypto) fires `purchase_failed` the same way the cron path does

  5. The two internal dedup/race-guard `status: "expired"` writes in `payment.service.modular.ts` (PAP sibling-supersede, free-$0-PAP stale-attempt supersede) never fire `purchase_failed` — no false failure events for purchases that actually succeeded

## Milestone Summary

**Decimal Phases:** None.

**Key Decisions:**

- One `purchase_failed` event for expired/cancelled/failed, differentiated via `reason`/`error_code` property (no separate `purchase_expired` event) — matches gateway-status normalization, avoids Klaviyo event-taxonomy bloat.
- Wire tracking emits ONLY at explicit gateway/cron call sites, never via model hook or status-keyed query — the two internal PAP supersede `expired` bulk-writes stay silent by construction (locked convention for any future payment-status tracking).
- Normalized errorCode vocabulary (`checkout_expired`/`card_declined`/`gateway_failed`/`cancelled`), never raw gateway decline strings — PII-adjacent + unbounded strings are bad for a third-party marketing tool.
- Stable `purchase_failed:<paymentId>` eventId (distinct namespace from `purchase:<paymentId>`) — webhook redelivery dedup without colliding with completion events.
- USD-normalized `value` from `usdAmount` only, `currency: "USD"` always — carries forward v1.3's JPY-as-USD guard.

**Issues Resolved:**

- Trading Cult's "expired purchase never reaches Klaviyo" (the ticket symptom) — root cause was `purchase_failed` existing as fully-registered dead scaffold with zero callers.
- Paysafe routing question (flagged unverified by research) — resolved during planning: routes through `PaymentService.handleCallback` → generic `handleNonCompletedPayment`, covered by 13-02 at zero extra cost.
- Klaviyo adapter silently dropping `errorCode`/`reason` from all event payloads.

**Issues Deferred:**

- 4 live-Klaviyo human-verify checks (cron-expiry event visible, Stripe failure w/ reason, redelivery no-dup, PAP supersede zero-noise) — gated on next main-2026 deploy.
- KLAV-05 language/locale Klaviyo property, KLAV-06 purchase-event enrichment, KLAV-07 PAP funded-leg failure audit, KLAV-08 Paysafe deep verification (routing already confirmed in practice) — v1.5 candidates, same source ticket.

**Technical Debt Incurred:**

- None new. Pre-existing scoped-tsc noise (Intercom/logger/config transitive imports missing esModuleInterop flags under ad-hoc invocation) documented, untouched.
