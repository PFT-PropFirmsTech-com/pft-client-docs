# RESEARCH: Phase 13.1 — Password Length DOS Fix

## Source

External pentest report (umer@barhamsec.com), 2026-07-03. Target: `app.xpips.com/auth/register`. Medium severity — bcrypt is O(2^cost) CPU-bound per hash; unbounded input length lets an attacker submit multi-MB passwords, amplifying per-request hashing cost and enabling a DOS via concurrent registration attempts.

## Root Cause

`pft-backend/src/app/modules/Auth/auth.validation.ts` — every password-bearing Zod schema enforces `.min()` but no `.max()`. Since `validateRequest` middleware runs Zod before the controller, and all these schemas are wired into their routes via `validateRequest(...)`, this is a single-file fix. Confirmed 4 unbounded fields, all reaching `bcrypt.hash()`:

| Schema | Field | Line | Current | Route | bcrypt.hash() call site |
|---|---|---|---|---|---|
| `registerUserValidationSchema` | `password` | auth.validation.ts:12 | `.min(6)`, no max | `POST /auth/register` | auth.service.ts:536 |
| `loginUserValidationSchema` | `password` | auth.validation.ts:52 | `.min(6)`, no max | `POST /auth/login` | N/A — compare only, but still worth capping (bcrypt.compare is also O(cost) over input) |
| `changePasswordValidationSchema` | `currentPassword` | auth.validation.ts:64 | `.min(6)`, no max | `POST /auth/change-password` | compare only |
| `changePasswordValidationSchema` | `newPassword` | auth.validation.ts:65 | `.optional()`, no min/max | `POST /auth/change-password` | auth.service.ts:1547 |
| `forgotPasswordValidationSchema` | `newPassword` | auth.validation.ts:103 | `.min(8)`, no max | `POST /auth/forgot-password` | auth.service.ts:1631 (via reset flow) |

Other bcrypt.hash() call sites (auth.service.ts:695, :1730) are internal-generated temp passwords, not user-supplied — out of scope.

Note: `changePasswordValidationSchema.newPassword` is currently `.optional()` with **no min at all** — a pre-existing separate weakness (empty/no length floor), but only the max-length DOS is in scope per phase goal. Do not expand scope to add a min there unless trivial to bundle (Claude's discretion at plan time — flag if touching this schema anyway).

## Recommendation

Add `.max(72, "Password must be at most 72 characters long")` to all 4 fields above. 72 is the OSWAP-recommended bcrypt-safe ceiling (bcrypt silently truncates at 72 bytes anyway, so this also fixes a latent correctness bug where passwords beyond 72 chars were being silently truncated by bcrypt with no user-facing signal).

This is a single-file, single-repo change (`pft-backend`). No frontend change required — the report's PoC just shows the server currently accepts oversized input; a 422 rejection is the fix.

## Deploy Note

Per project convention: `pft-backend` ships from `main-2026`. All brands (not just xpips) share the same `auth.validation.ts` — fix applies globally, not per-brand.

## Out of Scope

- Frontend maxlength attribute on the register form (defense-in-depth, not required to close server-side DOS — server validation is the actual fix)
- Per-brand config — this is shared backend code, no brand-specific toggle exists or is needed
- Rate limiting changes — `registerLimiter` already exists on the route; unrelated to this vuln
