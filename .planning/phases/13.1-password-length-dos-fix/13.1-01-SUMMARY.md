# Phase 13.1 Plan 01: Password Length DOS Fix Summary

**Closed an external DOS report by capping all 4 user-supplied password fields in pft-backend's Auth Zod schemas at 72 chars, rejecting oversized input with a 422 before bcrypt ever runs.**

## Performance

- **Duration:** ~6 min
- **Started:** 2026-07-03T12:41:00Z (approx, plan file timestamp)
- **Completed:** 2026-07-03T12:47:19Z
- **Tasks:** 2/2 completed
- **Files modified:** 1

## Accomplishments
- Added `.max(72, "Password must be at most 72 characters long")` to `registerUserValidationSchema.password`, `loginUserValidationSchema.password`, `changePasswordValidationSchema.currentPassword`, `changePasswordValidationSchema.newPassword`, and `forgotPasswordValidationSchema.newPassword` (5 occurrences across 4 fields).
- Verified via direct `safeParse` against the real exported `UserValidation` schemas (not a mocked/duplicated schema) that a 5000-char password is rejected with a `too_big` issue on the correct field path, and that a valid 12-char password still passes, across all 4 fields (11 total assertions, all green).
- Confirmed no scope creep: `git diff --stat` shows exactly one file changed; no `.min()` was added to `changePassword.newPassword`; no frontend/rate-limiter/per-brand config touched.

## Decisions Made
- 72-char ceiling chosen per plan spec (OWASP bcrypt-safe max, matches bcrypt's own silent-truncation point at 72 bytes).
- No `.min()` added to `changePassword.newPassword` — kept strictly in scope per plan instruction; flagged in RESEARCH.md as a separate future hardening item.
- Verification harness (Task 2) was written and run from the scratchpad directory, not the repo, per plan instruction — proves the fix using the actual exported schema objects via `ts-node --transpile-only` with CLI-overridden `module`/`moduleResolution` to work around the repo's `NodeNext` tsconfig setting outside its own root.
