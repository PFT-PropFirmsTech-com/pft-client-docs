<objective>
Every Klaviyo-bound tracking event that resolves to a real user carries that user's
language as a Klaviyo **profile** property (and mirrored as an event property),
derived from real user data via a defined fallback order — stored locale →
phone region → address country — and omitted entirely when none of those sources
resolves. Additionally, confirm the pre-existing `Language: ja` value seen on one
live Klaviyo profile is not produced by any second/hidden code path (KLAV-09).

Purpose: Trading Cult needs to segment Klaviyo audiences by client language (JP
campaigns). Location is an acceptable proxy per the client's follow-up, hence the
phone/country fallbacks. This satisfies KLAV-05 (language as a segmentable Klaviyo
profile property on every email-bearing event) and KLAV-09 (defined source order +
confirmed code ownership of the stray live property).

- New `deriveUserLanguage()` derivation util (omit-when-unknown).
- `language` field on `ITrackingEventPayload`.

  doc is already loaded there).
- Klaviyo adapter sets `Language` on the profile object + event `properties`.
- A documented KLAV-09 finding: the stray `Language: ja` is stale/one-off pre-existing
  data, not a live second code path.

  <name>Task 1: Add deriveUserLanguage() derivation util (source order, omit-when-unknown)</name>
  <files>pft-backend/src/app/utils/language.util.ts</files>
  <action>
    Add a new exported function `deriveUserLanguage` to language.util.ts (append after
    the existing exports; do NOT modify `normalizeLanguage`/`isNonDefaultLanguage`/
    `isBlankHtml`, other code depends on their "always returns 'en'" behavior).

    Signature:
    ```ts
    export function deriveUserLanguage(user: {
      preferredLanguage?: string | null;
      phone?: string | null;
      country?: string | null;
      countryCode?: string | null;
    } | null | undefined): SupportedEmailLanguage | undefined
    ```

    Behavior — apply the source order EXACTLY, returning the first that resolves,
    and `undefined` if none does (NEVER default to "en" here — that is the whole
    point vs. normalizeLanguage):

    1. **Stored locale (highest priority):** if `user.preferredLanguage` is a non-empty
       string, run it through the recognition logic and return the matched language.
       Reuse `normalizeLanguage`'s recognition rules BUT do not accept its "en" default
       as a real signal blindly — since our supported set is exactly ["en","ja"] and any
       explicitly-stored preferredLanguage (even "en") IS real user data, a non-empty
       preferredLanguage should return `normalizeLanguage(user.preferredLanguage)`
       (an explicitly stored "en" is a legitimate value, not a guess).

    2. **Phone region:** else, if `user.phone` is a non-empty string, derive the ISO
       country via the existing phone parser. Import `validatePhone` from
       `./phone` and call `validatePhone(user.phone)` — use its `.country` (ISO-3166,
       e.g. "JP"). Map that ISO country to a supported language via a small closed
       COUNTRY_TO_LANGUAGE map (see below). Return the mapped language if the country
       is in the map; if the phone yields a country NOT in the map, do NOT return "en"
       here — fall through to step 3 (a French phone is not evidence of English;
       omission is correct unless country later maps).

    3. **Address country:** else, if `user.country` or `user.countryCode` is a non-empty
       string, map it through the same closed COUNTRY_TO_LANGUAGE map (country field may
       be a full name like "Japan" OR an ISO code like "JP"/"JPN" depending on brand — so
       the map/lookup must tolerate both: normalize the input to uppercase, try exact ISO2
       match, then a small name→ISO alias for the languages we care about, e.g. "JAPAN"→"JP").
       Return the mapped language, else `undefined`.

    4. If nothing resolved: return `undefined`.

    Add the closed map near the top of the function/module — keep it MINIMAL and
    documented as "expand as more localized campaigns are added". Only the languages
    we actually support (en, ja) need entries; since "en" is the default email language
    it is NOT a segmentation target on its own, so the map's real job is to detect JA
    markets. Concretely:
    ```ts
    // ISO-3166-alpha2 country → supported language. Closed set — expand only when a
    // new localized market/campaign is added. Countries absent from this map yield
    // no language signal (omission), never a guessed default.
    const COUNTRY_TO_LANGUAGE: Record<string, SupportedEmailLanguage> = {
      JP: "ja",
    };
    // Minimal full-name → ISO2 aliases for the `country` free-text field.
    const COUNTRY_NAME_TO_ISO2: Record<string, string> = {
      JAPAN: "JP",
      JPN: "JP",
    };
    ```

    Do NOT add any npm dependency — `validatePhone`/`libphonenumber-js` already exist.
    Guard every branch defensively (try/catch around validatePhone is unnecessary —
    validatePhone already never throws and returns country:null on bad input; just
    check the returned `.country` for null).
  </action>
